MCP app tools and auth

Expose app actions to AI through the platform MCP server. Apps declare actions in mcp.json; ProAppStore handles tool discovery, authenticated calls, SQL execution, and per-user scoping.

Current implementation

Apps do not need to implement their own MCP server for normal D1-backed app actions. The app-owned surface is the mcp.json action manifest. The platform MCP server at https://mcp.proappstore.online/mcp is the canonical integration point.

  1. Your app declares tools in an mcp.json manifest at the repo root.
  2. On publish, those tools are registered to the backend app_tools table.
  3. The platform MCP server loads registered tools and exposes each as <app_id>/<tool_name>, discoverable with discover_tools.
  4. When called, the server runs the tool SQL against data-<app>.proappstore.online using the caller's session.

Authentication model

All app-data tools should be authenticated unless they are deliberately public. In the production manifest format, auth is represented by:

{ "requires_auth": true }

When an authenticated MCP connection calls a tool, the platform MCP server has the caller's PAS session token and user id. It injects magic placeholders such as :__user_id, :__now, and :__uuid, then sends the prepared SQL to the app data worker with the caller's bearer token.

Authentication answers who the user is. Authorization still belongs in the SQL or app data model. Scope reads and writes with :__user_id and app-specific permission checks:

WHERE EXISTS (
  SELECT 1 FROM memberships
  WHERE org_id = :org_id
    AND user_id = :__user_id
    AND role = 'manager'
)

This prevents a caller from passing someone else's org_id and reading or mutating data they do not manage.

Roles and permissions

PAS provides reusable roles through the SDK (app.roles). Those roles are the right abstraction for coarse permission gates such as owner, moderator, editor, viewer, manager, or custom app roles.

The current mcp.json registration API does not yet enforce role fields in the manifest. Until role-gated manifest fields are implemented, enforce permissions with one of these patterns:

  • Use :__user_id in SQL and check app-domain membership tables, such as an org_id membership row.
  • Use app data that mirrors PAS roles if the tool needs role-specific access.
  • Keep all tools that touch user or app data marked with requires_auth: true.

The intended manifest extension is explicit auth metadata:

{
  "auth": {
    "required": true,
    "platform_roles": ["creator"],
    "app_roles": ["manager"]
  }
}

That extension is not a substitute for row-level checks. A user can have a manager role somewhere and still not manage the specific organisation named by :org_id. Use role metadata for early rejection and better UX; use SQL scoping for the final data permission check.

Manifest example

{
  "tools": [
    {
      "name": "list_items",
      "description": "List the signed-in user's items, newest first",
      "operation": "query",
      "sql": "SELECT id, title, created_at FROM items WHERE user_id = :__user_id ORDER BY created_at DESC LIMIT :limit",
      "params": {
        "limit": { "type": "integer", "default": 50, "max": 200, "optional": true }
      },
      "requires_auth": true
    },
    {
      "name": "create_item",
      "description": "Create an item for the signed-in user",
      "operation": "execute",
      "sql": "INSERT INTO items (id, user_id, title, created_at) VALUES (:__uuid, :__user_id, :title, :__now)",
      "params": { "title": { "type": "string" } },
      "requires_auth": true
    }
  ]
}

Manifest fields

FieldMeaning
nameLowercase a-z0-9_. Exposed as <app_id>/<name>.
descriptionWhat the tool does. The model reads this to decide when to call it.
operationquery is one SELECT. execute is one INSERT, UPDATE, or DELETE.
sqlOne parameterized statement against the app's own D1 tables. Bind values with :name placeholders.
paramsDeclared inputs. Types: string, integer, number, boolean.
requires_authtrue means the call needs a session token. SQL using :__user_id must require auth.

Use requires_auth: true for every app-data tool unless the data is genuinely public. For user-scoped and organisation-scoped apps, that normally means every tool, including reads.

Magic placeholders

PlaceholderResolves to
:__user_idThe calling user's id. Scope per-user rows with WHERE user_id = :__user_id.
:__nowCurrent time, in milliseconds since epoch.
:__uuidA fresh UUID for inserted primary keys.

Validation rules

  • SQL must start with SELECT, INSERT, UPDATE, or DELETE.
  • No DDL, no semicolons, and no multi-statement SQL.
  • UPDATE and DELETE must have a WHERE clause.
  • query must use SELECT; execute must not.
  • Every SQL parameter must be declared in params, unless it is a magic placeholder.
  • If SQL uses :__user_id, requires_auth must be true.
  • Max 50 tools per app.

Registration

  • CLI apps: pas publish reads mcp.json and calls the owner-authenticated app tool registration endpoint.
  • Agent-built apps: the Agent Teams deploy stage auto-registers mcp.json after a green deploy once the app data plane exists.

If an app ships no mcp.json, nothing is registered. Removing the manifest and redeploying clears the app's tools.

Calling tools

Point any MCP client at the platform server:

{
  "mcpServers": {
    "proappstore": {
      "command": "npx",
      "args": ["mcp-remote", "https://mcp.proappstore.online/mcp"]
    }
  }
}

Then discover_tools lists registered app tools, and <app>/<tool> calls one. Tools marked requires_auth need a session token on the connection, so the call runs as that user.

Security model

  • App-data tools are authenticated by default. Public tools should be intentional and rare.
  • A tool can only run its one parameterized SQL statement against the app's own D1 database.
  • Inputs bind as parameters; tools must not string-build SQL.
  • :__user_id plus requires_auth keeps data scoped to the calling user.
  • Role-aware authorization is enforced in SQL today. Manifest role gates are the next extension.
